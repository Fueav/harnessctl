# v0.4.0 Migration

v0.4.0 adds three backward-compatible commands and profile schema v3. Existing v1 and v2 consumers continue to run on their pinned engine; they do not gain the new convergence contract until migrated.

## Consumer changes

1. Pin `harness/harness.lock` to `v0.4.0`.
2. Change `harness/harness_profiles.json` to schema 3.
3. Remove the `nightly` profile and remove `nightly` from `conditional_gates.*.always_profiles`; scheduled jobs invoke `verify release`.
4. Give every expensive repository command its own custom gate. Put path-selected gates in `conditional_gates`; do not hide multiple suites behind one custom command.
5. Render `harness/scaffold.lock` with `harnessctl scaffold record` after semantic decisions, then require `harnessctl scaffold audit` to pass.
6. After candidate or release verification, use `harnessctl evidence verify` for later use of the same clean commit instead of rerunning the suite.

## Compatibility and rollback

- Profile schemas 1 and 2 remain accepted by v0.4.0.
- `verify`, `check`, `approval finalize`, and generated evidence schema 1 retain their existing command shapes.
- Rolling back the binary requires restoring the prior engine lock and schema-2 profile together. A schema-3 profile intentionally fails closed on older binaries.
